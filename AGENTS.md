## Architecture summary

- Boot is a **linear FreeRTOS task chain**: `TaskInit → TaskConfigAndLog → TaskSysControl → TaskCC1101 → TaskMQTT → TaskWeb`, single core. Task-chain signaling is mostly polled global flags plus a few real mutexes/semaphores; the only FreeRTOS queue is the I2C sniffer's ISR event queue (`gpio_evt_queue`, `main/ithodevice/i2c_sniffer.cpp`).
- Hardware/network/RF/I2C access goes through **global manager singletons** (`main/managers/*`, e.g. `rfManager`, `i2cManager`).
- Device support is a **data table** (`ithoDevices[]` in `main/ithodevice/IthoDevice.cpp`), not a class hierarchy.
- REST API v2 splits **pure logic** (`processXxx` in `main/api/WebAPIv2.cpp`) from **HTTP routing** (`handleXxx` in `main/api/WebAPIv2Rest.cpp`) — this is what makes native unit testing possible. MQTT (`main/api/MqttAPI.cpp`) reuses the same logic layer.
- Config persists to **LittleFS JSON**; before a flash repartition (which wipes LittleFS) all config types are snapshotted to **NVS** (`backupAllConfigs()`) and restored on the next boot.

Full detail and evidence: [docs/adr/README.md](docs/adr/README.md) (ADR-0002 through ADR-0009).

## Build commands

Run from `software/NRG_itho_wifi/`. `pio` may not be on `PATH` — try `pio` first, then `~/.platformio-venv/bin/pio` or `~/.platformio/penv/bin/pio` if not found (CI installs via `pip install platformio`).

```bash
pio run -e dev       # local development build (serial logging enabled)
pio run -e beta      # beta firmware build
pio run -e release   # stable firmware build (what CI builds)
```

## Test commands

```bash
pio test -e native_test              # host-side unit tests (also run in CI)
pytest tests/api --device <ip>       # live-hardware REST tests (manual, needs a real device)
ITHO_DEVICE=<ip> pytest tests/mqtt   # live-hardware MQTT tests (manual)
```

Two-tier testing detail: [.ai/testing-strategy.md](.ai/testing-strategy.md).

## Common mistakes to avoid

- Editing anything under `software/lib/` — it's vendored, pin a different version in `platformio.ini` instead.
- Hand-editing `main/webroot/*_gz.h` — generated by `build_script.py` from `main/webroot_source/`; edit the source and rebuild.
- Assuming FreeRTOS queues exist for task signaling — they don't; it's polled flags (see [ADR-0004](docs/adr/ADR-0004-freertos-linear-task-chain.md)).
- Assuming `main/ithodevice` is a class hierarchy — it's a data table (`ithoDevices[]`); add a device via a new row + label header, not a subclass.
- Inlining REST business logic in an `AsyncWebServer` route lambda — breaks the logic/routing split that makes native testing possible ([ADR-0006](docs/adr/ADR-0006-rest-api-v2-logic-routing-split.md)).
- Renaming/removing an MQTT topic or REST path without treating it as a breaking change for HA/Homey/Domoticz integrations ([ADR-0005](docs/adr/ADR-0005-mqtt-integration-design.md)).

## Coding guidelines

C++20 (`gnu++2a`), `-Wall -Wextra`, `-Os` (flash/RAM constrained — avoid heavy abstractions). Naming: `TaskX` (tasks), `processXxx` (API logic), `handleGetXxx`/`handlePostXxx` (routes), `<name>Manager` (manager singletons), `load*Config`/`save*Config` (persistence). Full list: [.ai/coding-standards.md](.ai/coding-standards.md).

## Development workflow

1. Check [specs/index.md](specs/index.md) for an existing spec covering the change; if none and it's a feature/bugfix/refactor/API change, create one from [specs/templates/](specs/templates/) first.
2. If the change is architecturally significant (task structure, manager, device model, REST/MQTT surface, config format, hardware abstraction), check/update the matching ADR — trigger table in [docs/adr/README.md](docs/adr/README.md).
3. Implement, following the patterns in [.ai/common-patterns.md](.ai/common-patterns.md).
4. Add tests per [.ai/testing-strategy.md](.ai/testing-strategy.md); update the spec's test-requirements checklist.
5. Update `docs/architecture/repository-map.md`/`.ai/architecture-summary.md` if they're now stale; move the spec to `specs/completed/`.

Branching/commit conventions: [.ai/development-workflow.md](.ai/development-workflow.md). Release process: [.ai/release-process.md](.ai/release-process.md).
